## Часть 1 — проверка «5 причин внешнего запуска»

Стек реальный: `launch.sh` → `sandbox-run.sh` (bwrap: `--ro-bind / /`, `--tmpfs $HOME`,
tickets `--ro-bind`, repo rw, `--unshare-pid/uts`, `--die-with-parent`) → `launcher/stanok.py`
(`verify_gate()` стр. 233, `<contract_lock>` стр. 446). Причины 2, 3, 4 — верные и сильные:

- 2 (внешний fail-closed судья): python видит физический rc=0 от `node --test`; LLM не может
  «доложить готово». Сохраняется.
- 3 (bwrap-изоляция ОС): настоящая, kernel-level. Есть.
- 4 (монополия на слот): пока супервайзер спит-poll'ит, он не шлёт запросов — станок один
  генератор. Верно.

Причина 1 (наследование контекста) — слабейшая. Факты из кода:
- `runAgent.ts:370-373`: `contextMessages = forkContextMessages ? ... : []` — по умолчанию
  история НЕ наследуется.
- `AgentTool.tsx:513-534`: нормальный системный промпт субагента = `selectedAgent.getSystemPrompt()`
  + env-детали. НЕ системный промпт родительской сессии.
- Полное наследование — явный экспериментальный `fork` (`forkSubagent.ts`, `AgentTool.tsx:495-512`),
  выключен по умолчанию; его цель — «cache-identical API request prefixes», а не «удобно форкнуть».
- Реальная причина, почему субагент-внутри НЕ эквивалентен внешнему станку — не «раздутый
  контекст», а: (а) project-конфиг: субагент живёт в projectDir родителя → `stanok/.claude/
  settings.stanok.json` (bash-gate, verifier, test-lock, malware-scan) НЕ загружаются; (б) нет
  bwrap (Bash родителя = хост, «честное слово промпта»); (в) гейт не физический.

## D1 — Нативный «StanokAgent»-субагент: инфраструктура ЕСТЬ, но это замена изоляции на доверие

Что реально в 2.1.88:
- Вход Agent-тула: `description`, `prompt`, `subagent_type`, **`cwd`** (override рабочей
  директории, «Absolute path… overrides the working directory for all filesystem and shell
  operations»), `isolation: worktree`, `run_in_background` (`AgentTool.tsx` схема ~83-149).
- Кастомные агенты из `.claude/agents/*.md` (`loadAgentsDir.ts`); `stanok/.claude/agents/` есть.
- **`cwd`-override → runAgent пересобирает системный промпт в этом cwd** (`AgentTool.tsx:618-626`:
  `override: cwd ? undefined`, `runAgent.ts:508-518` + `wrapWithCwd`), т.е. субагент в
  `cwd=stanok/` прочитал бы `stanok/CLAUDE.md` и компактный промпт агента.
- per-agent `permissionMode`, async-агенты с собственным abort, `SubagentStart`-хуки.

Вывод: механически сделать «субагент-станок с чистым контекстом и своим cwd» можно. НО:
- теряется слой bwrap и project-хуки stanok (см. Часть 1); субагент наследует permission-режим
  родителя/`bubble` — управление «по доверию».
- внешний процесс позволяет запускать тикеты ДЕТАЧ-режимом без живого супервайзера.
- ВАЖНО: станок УЖЕ использует нативные субагенты внутри своей сессии (reviewer/tester —
  шаги 5-6 CLAUDE.md, Agent tool). Вопрос текста — только про ВЕРХНИЙ уровень оркестрации
  (тикет-прогон как субагент супервайзера). Это меняет раннер, но НЕ трогает думание и
  субагентские стоимости — измеренный боттлнек.
- Вердикт: держать как sandbox-пилот при желании «нативный запуск из TUI», приоритет НИЗКИЙ.

## D2 — Заморозка префикса (KV-cache): реально, код уже под это спроектирован

- fork-путь существует ради «cache-identical API request prefixes» (`AgentTool.tsx:485-488`).
- Признанный источник развала кэша: сериализация tool-def. Комментарий `AgentTool.tsx:613-616`:
  permission-режим `bubble` меняет сериализацию тулов → префикс расходится на первом отличающемся
  туле. useExactTools наследует thinkingConfig.
- Динамика в system-контексте: `context.ts:186` `currentDate = 'Today's date is …'` — меняется
  раз в сутки; `getUserContext/getSystemContext` пересчитывают CLAUDE.md, git status, env-детали
  (`enhanceSystemPromptWithEnvDetails`). Пересчёт = сдвиг префикса.
- Наш опыт согласуется: reasoning_effort/шаблон/tool-def меняли префикс → весь KV-кэш llama-server.
- Что можно: замерить hit-rate префиксного кэша на сервере (logs / llama-server prompt cache),
  заморозить «шумные» поля контекста (периодический git status refresh). Риск: модель потеряет
  актуальное окружение — нужен замер, не слепое отключение. Вердикт: СРЕДНЯЯ-ВЫСОКАЯ ценность,
  измеримо на нашем стеке. Самое «исследуемое» направление.

## D3 — Клиентский мьютекс для `--parallel 1`: не то

- `messageQueueManager.ts` — очередь ВВОДА пользователя, не сетевой мьютекс.
- Внутри сессии запросы последовательны (блокирующий главный цикл). Параллельность дают только:
  async/background-агенты (`run_in_background`, teammates) и — главное — РАЗНЫЕ процессы
  (супервайзер + станок) на одном слоте сервера.
- Патч клиента видит только свой процесс → глобально cross-process не замьютексит. Реальные
  фиксы: `--parallel > 1` / отдельный инстанс / серверная очередь. Проблема CC-041
  (KV-резидентность контекста супервайзера) решается слотами или кэшем, не мьютексом.
- Фактическая ошибка текста: «4 паразитных вызова TaskCreate/TaskUpdate в единственный слот».
  Task*-тулы ЛОКАЛЬНЫЕ (персистентный task-list), в настройках станка они в deny. Слот сервера
  они не занимают в принципе.
- Вердикт: закрыть.

## D4 — «Вшитый» TDD pre-return: частично, но цель недостижима

- Хуки реальны: `Stop`/`SubagentStop` (`utils/hooks.ts:3653-3682`), `PostToolUseFailure`,
  `PreCompact`, `Notification`, `PermissionDenied`. У нас уже работает PostToolUse-verifier
  (`verifier.sh`) → модель видит `VERIFY: FAIL <причина>` СРАЗУ после Write/Edit и чинит в
  той же сессии — это и есть механизм CLEAN-FIRST.
- Stop-хук терминальный: срабатывает при завершении, новых ходов не создаёт. «Не отдавать
  управление супервайзеру, пока тест красный» из Stop-хука НЕЛЬЗЯ — для ретрая нужен новый
  ход, а хуки ходы не порождают.
- Физический fail-closed гейт (python видит rc=0, `<contract_lock>`, reset дерева) требует
  внешнего судьи. Вердикт: PostToolUse-verifier — правильная точка (уже стоит); внешний
  verify_gate остаётся. Реально в-scope: Stop/SubagentStop-хук как финальный контроль rc и
  семантики выхода, но не замена раннера.
