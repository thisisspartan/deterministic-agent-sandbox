# SPEC-HOSTSIDE-WORKFLOW — режим исполнения host-side работ (решение оператора, 2026-10-14, окончательное)

Два раздельных режима разработки. Не два уровня полномочий внутри одного worker.

## 1. Граница

- **Machine worker** — обычные машинные тикеты, write-поверхность без изменений:
  `src/`, разрешённая часть `tests/`, `docs/`, `scripts/run.sh`. Права worker НЕ расширять.
- **Trusted operator-side coding session** — отдельная доверенная сессия разработки с явно
  предоставленным доступом к host-side коду: `launcher/`, `k8s/*.tmpl`, supervisor/session-код,
  инструменты оператора. Реализует согласованное изменение в отдельной ветке/worktree.

Host-side изменения НЕ исполняются Stanok как машинные тикеты. Оператор утверждает требование,
проверяет diff, принимает результат через существующие тесты. `tests_harness`/doctor — обязательная
часть приёмки, но не единственное доказательство. Эксплуатационные действия (деплой на кластер,
переключение блокирующих политик) — отдельные явно утверждённые операции оператора, не часть тикета.

## 2. Отнесение работ (очерёдность не меняется: G1 → G2 → G4 → context-verdict → PSA/G3)

| Работа | Режим |
|---|---|
| G1 CPU/RAM requests+limits в `worker-job.yaml.tmpl`, `fresh-job.yaml.tmpl` | host-side |
| G2 read-only агрегатор evidence | host-side |
| G4 формат тикета/контракт acceptance-тестов | контрактная часть — machine тикет после согласования семантики; runtime/транспорт — только если нельзя выразить существующей схемой |
| Context verdict (WARN→STOP) | host-side, только после данных G2 |
| PSA namespace-метки | host-side; `enforce` на живом namespace — действие оператора |
| G3 риск-поле тикета + правила спецификации | контрактная часть — machine тикет; diff-сверка в Patch Gate — host-side, на существующих `changes.patch`/manifest, без нового path-scanner |

## 3. Принятые фактические поправки (к плану от 2026-10-14)

1. `CONTEXT-ROT`/`PREFIX-BREAK` — только `log()` (session.py:569,574), в `summary.json` нет.
   Публикуются: `_publish_evidence` копирует `summary.json`, `launcher.stdout.log`,
   `failures.log` в `evidence/<label>/` (summary.py:74). Агрегатор читает опубликованные логи;
   парсер — по стабильным маркерам `[CONTEXT-ROT WARN]` / `[PREFIX-BREAK WARN]`, не по
   человекочитаемому тексту. Новая телеметрия не добавляется.
2. Одноузловой k3s: requests не выбирают ноду; их роль — допустимость размещения относительно
   allocatable, доля CPU при конкуренции, участие в node-pressure eviction. limits —
   throttling / OOM. QoS-класс предсказывает поведение, не абсолютная защита. Числа — по
   измерениям; `kubectl top` не источник пикового RSS (редкое сэмплирование); при отсутствии
   истории пиков — запас + проверка OOM/throttling после внедрения. Для fresh-check — отдельные
   меньшие значения, если измерения подтверждают.
3. G4: contract lock (существующие `tests/**`, `scripts/run.sh`) + fresh-check уже дают
   неизменность и независимую проверку кандидата — не дублировать. Пробел — в контракте тикета:
   нет различия acceptance-тестов (доверенные, фиксируются до запуска) и тестов агента (TDD-обратная
   связь). Holdout — дополнительная ступень для высокого риска, не дефолт. Тест не становится
   доверенным потому, что его создал и зафиксировал тот же агент.
4. Предупреждения CONTEXT-ROT (деградация на длинном входе) и PREFIX-BREAK (разрыв KV-префикса) —
   разные сигналы; stop-политика CONTEXT-ROT автоматически к PREFIX-BREAK не применяется.

## 4. Приёмка (кратко; полные критерии — в решениях оператора 2026-10-14)

- **G1:** оба шаблона рендерятся; doctor+тесты; server-side dry-run; репрезентативная задача без
  OOM и неприемлемого throttling; доступность k3s/supervisor не ухудшается; retry-логика и остальное
  в шаблонах не затронуты.
- **G2:** читает реальные evidence без изменения файлов; fixtures (PASS/FAIL/timeout/предупреждения/
  отсутствующие поля/битый JSON); неизвестное не превращается в фиктивный вердикт; отчёт указывает
  размер выборки; doctor+тесты.
- **G4:** схема контракта тестирована; существующие тикеты корректны или мигрированы явно;
  доверенные тесты фиксируются до запуска; вердикт — существующий fresh-check + acceptance-проверки
  контракта.
- **Context verdict:** решение по данным G2 (оставить WARN / продолжать сбор / STOP по измеренному
  порогу); regression-тесты; корректная причина завершения в сводке; без неявных повторов после STOP.
- **PSA:** зафиксировать версию k3s → версию профиля; warn/audit → проверка обоих Pod → enforce.
