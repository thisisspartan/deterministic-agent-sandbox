## Режим отказа барьера 2 (инцидент CC-214, evidence/cc214-wt)
cli.js безусловно добавляет `.claude/settings.local.json` в deny-лист (самозащита
permissions). bwrap bind'ит `/dev/null` поверх deny-пути; для несуществующего файла
создаёт mount point → внутри контейнера `.claude/` = `:ro` → EROFS → отказ каждого
Bash-вызова. В свежем worktree файла нет (gitignored) — сломался именно worktree-прогон;
в главном дереве файл существует, bind проходит. Настройками не лечится: deny built-in;
`enableWeakerNestedSandbox` (cli.js offset 4348420: `if(!j) --proc /proc`) решает только
`--proc`; `failIfUnavailable` (FC_) проверяет наличие бинарников, per-call EROFS не ловит —
молчаливый отказ при rc=0.

## Нативные примитивы (cli.js 2.1.88, §7)
- `sandbox.enabled` → `AT8`/`wT8`: `false` полностью отключает обёртку (`Y54`:
  `if(!_&&!f&&!G) return K`). Штатный выключатель.
- `enableWeakerNestedSandbox` (`k54` → `Y54.j`): вложенный режим, пропускает `--proc`
  (у нас уже `true`).
- Примитива отключить built-in deny settings-файлов — нет.

## Барьеры: уточнения
- **Факт, которого не было в раунде 1:** seccomp/apparmor контейнера = `unconfined` —
  ослаблены ради вложенного bwrap (коммит `984eb7d`: «required for bwrap inside the
  container, verified empirically», `sandbox.py:161-167`). Вариант C обзора — не новая
  опция, а текущее состояние с unconfined seccomp.
- Дефолтный seccomp поверх cap-drop=ALL + no-new-privileges + non-root + `:ro`-mounts
  добавляет защиту только от «злого» Bash (побег через экзотические syscall); в модели
  угрозы «случайные записи/ослабление тестов» он не добавляет ничего.
- Эксперимент «заведётся ли bwrap под дефолтным seccomp»: исторический ответ уже есть
  (984eb7d — unconfined необходим); ожидаемый результат — падение (bwrap нужны user
  namespaces). Ценность только в явной фиксации.
- **Новый факт (cli.js 2.1.88):** нативного «уже в песочнице — не оборачивать» нет.
  `CLAUDE_CODE_BUBBLEWRAP`/`getIsBubblewrapSandbox` используются только для root-проверки
  `--dangerously-skip-permissions`; `wT8`/`nC_` оборачивают безусловно при
  `sandbox.enabled=true`. Единственный штатный выключатель — `sandbox.enabled:false`.
- Сетевой узел: `--network=none` невозможен — CLI машины работает в контейнере и должен
  достигать сервер 192.168.8.131. «Сеть на стороне контейнера» = фильтрующий прокси
  (новый механизм) или принятие host-сети.
- Эмпирический вопрос перед выбором A/B: использует ли Bash машины сеть вообще? Стек —
  «no external dependencies», pytest предустановлен в образе, все тикеты stdlib.
  Проверка: grep по `evidence/` на pip/npm/curl — один шаг, ни одного прогона. Если сеть
  не используется, allowlist защищает неиспользуемую возможность → B резко дешевеет.
- Возражение к порядку обзора («сначала seed settings.local.json, потом эксперимент C»):
  seed — workaround барьера 2; платить за него до решения по барьерам — починка слоя,
  который, возможно, убирается. Порядок: сначала вопрос о сетевом фильтре → потом seed (A)
