# SPEC-PSA — Pod Security Admission для namespace станок-Job'ов (2026-10-14)

Работа из очереди PSA/G3 (SPEC-HOSTSIDE-WORKFLOW-2026-10-14 §2: «PSA
namespace-метки — host-side; enforce на живом namespace — действие оператора»).
Primitive-first (CLAUDE.supervisor §7): PSA — нативный механизм kube-apiserver
(GA с 1.25); мы НЕ реализуем проверку hardening в launcher — конфигурируем
нативный профиль. Существующие hardening-тесты (test_k8s_manifests) остаются;
PSA добавляет enforcement на уровне admission, независимый от нашей воли.

## 1. Зафиксированные версии (проверено командами 2026-10-14)

- k3s server: `v1.36.5+k3s1` (kubectl version; client та же). PSA GA,
  профильная версия — v1.36 (current). Профили: privileged / baseline / restricted.
- Namespace: `default` (значение по умолчанию `STANOK_K8S_NAMESPACE`, k8s.py:312).
  Меток PSA нет → для PSA это enforce=privileged (не-enforced), audit/warn=baseline.
  В default других workload нет (kubectl get pods/jobs -n default: пусто);
  kube-system от PSA освобождён.
- Оба Pod-шаблона (worker-job.yaml.tmpl, fresh-job.yaml.tmpl) уже удовлетворяют
  профилю restricted: runAsNonRoot+runAsUser 10001, allowPrivilegeEscalation:false,
  capabilities drop ALL, seccomp RuntimeDefault, readOnlyRootFS, нет hostPath /
  hostPorts / privileged; volumes — только configMap/emptyDir. runtimeClassName:
  gvisor (default-рендер CC-256) на PSA не влияет — PSA проверяет admission.

## 2. Процедура (этапы)

1. **warn/audit (host-side работа):** метки
   `pod-security.kubernetes.io/warn: restricted`, `pod-security.kubernetes.io/audit: restricted`
   на namespace — манифест `stanok/k8s/namespace.yaml` + применение к живому
   namespace. Никаких отказов Pod ещё нет: API только предупреждает/пишет audit.
2. **Проверка обоих Pod (host-side):** Pod-only извлечение из обоих шаблонов
   (текст-вырезка блока `template:` + подстановка {{VARS}} dummy; securityContext
   в шаблонах статичен) → `kubectl apply --dry-run=server` → ожидаем НОЛЬ PSA-
   предупреждений. Негативный контроль: заведомо нарушающий Pod (runAsUser 0)
   обязан дать PSA warning — иначе проверка не доказана.
3. **enforce (действие оператора, отдельное):** добавить
   `pod-security.kubernetes.io/enforce: restricted` к меткам живого namespace.
   Не часть этой работы; только после этапа 2 и явного решения оператора.

## 3. Приёмка

- `k8s/namespace.yaml`: kind Namespace, name default, метки warn/audit=restricted,
  enforce ОТСУТСТВУЕТ (запиновано тестом — добавление enforce = отдельное
  решение оператора с явной правкой теста).
- test_k8s_manifests: секция PSA пиновает содержимое namespace.yaml.
- Dry-run обоих Pod под warn/audit: ноль PSA-предупреждений; негативный контроль
  даёт предупреждение.
- Шаблоны Job не изменены (они уже restricted-чистые); doctor + harness зелёные.

## 4. Остаточные ограничения

- PSA проверяет admission, не рантайм; gVisor-изоляция ортогональна.
- Метки действуют на весь namespace `default`: будущие чужие workload в default
  тоже попадут под профиль (сейчас их нет). Альтернатива — отдельный namespace
  `stanok` (STANOK_K8S_NAMESPACE уже поддерживает) — не вводится без решения
  оператора.
- enforce на живом namespace — кластерная операция вне репозитория; манифест
  описывает желаемое состояние, применяет оператор.
