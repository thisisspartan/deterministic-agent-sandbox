## Разрешение (10:05–10:18 UTC, прогон fire3d-clearfix-retry1, диск-лог ~/llama-server.log)

Сервер перезапущен чистым; www.js пишет на диск (`~/llama-server.log`, 4349 строк).
Таймлайн из лога:
1. 10:05:57 — ход 1 станка (task 8298, 12698 токенов fresh) → завершён за 18с (10:06:15, 142 gen, truncated=0).
2. 10:06:15–10:17:47 — непрерывная цепочка 17 запросов (tasks 8397→16750), контекст растёт
   12841→47946 (cached-префикс каждого следующего = n_tokens предыдущего) — это РАБОТА станка
   (tool-calls внутри одного хода), сервер отвечает на каждый запрос штатно.
3. 10:17:48–10:18:02 — всплеск 14 отмен (tasks 19106…19236, ~0.5с интервал) — сработал
   `TURN_TIMEOUT_S=720` раннера (старт хода 10:05:57 + 720с ≈ 10:17:57) → interrupt SDK.

**Корневая причина (УСТАНОВЛЕНА):** не завис сервера/KV/SDK, а слишком короткий per-turn таймаут
раннера: один ход станка (17 API-вызовов, 11.5 мин работы) превысил `TURN_TIMEOUT_S=720`.
summary.json: rc=1, TURN-TIMEOUT, токены 0 (usage не записан из-за прерывания).
Гипотезы A/B/C как объяснение этого сбоя — отклонены; они могли объяснять только
первый сбой 08:47 (без логов).

**Исправление:** дефолт `TURN_TIMEOUT_S` в `stanok/launcher/stanok.py` 720 → 1200с
(override через `STANOK_TURN_TIMEOUT_S` сохранён). Ретрай: fire3d-clearfix-retry2.

**Результат:** fire3d-clearfix-retry2 — PASS (rc:0, CLEAN-FIRST, 177с, 1 ход, cache 93.8%). CC-043 DONE.
