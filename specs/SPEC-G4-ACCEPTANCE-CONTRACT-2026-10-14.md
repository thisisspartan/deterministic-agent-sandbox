# SPEC-G4 — минимальный контрактный механизм независимых acceptance-тестов (2026-10-14)

Trusted operator-side coding session (SPEC-HOSTSIDE-WORKFLOW-2026-10-14).
Реализация: `stanok/launcher/` (ticket/plan/cli/k8s/verify/summary). Без нового
верификатора, без второго AI-reviewer, без holdout, без новой инфраструктуры
хранения тестов. Не расширяет права worker.

## 1. Где сейчас определяется окончательный PASS (факт цепочки)

1. Worker Pod, каждый ход: `verify_gate` (launcher/verify.py) — позитивный
   контракт на declared-пути тикета + `run.sh list` + `run.sh test --all`.
2. Host, после Job: scratch-пересчёт contract lock
   (`scratch_contract_violations` против pre-run `contract_snapshot`) —
   изменение/удаление защищённого файла или undeclared-файл в tests/|src/
   ⇒ CONTRACT-FAIL независимо от worker-отчёта.
3. Host, fresh Job (`_fresh_job`, deny-all, без модели): тот же
   `run.sh list; run.sh test --all` на дереве = pre-run tree + changes.patch.
   Ноль — FRESH-FAIL.
4. `_publish_evidence`: приоритет вердикта CONTRACT-FAIL > FRESH-FAIL >
   утверждения worker; rc-выравнивание; патч на живое дерево только при
   финальном PASS (rc=0, нет violations, fresh зелёный).

Пробел: для нового тикета suite — тесты, которые написал сам агент
(`test:` из его тикета). Окончательный PASS обоснован агентскими тестами;
никакое независимое свидетельство в контракте не требуется и не фиксируется.

## 2. Контракт `accept:` (минимальный механизм)

Новый вид заголовка тикета: `accept: <path>` — доверенная acceptance-проверка.
`accept: none` — явное объявление «независимых acceptance-тестов нет».

Семантика mode (фиксируется в summary.json, поле `acceptance`):
- `provided` — ≥1 accept-путь объявлен;
- `none` — явно объявлено отсутствие;
- `undeclared` — accept-строк нет (обратная совместимость со всеми
  существующими тикетами; отсутствие НЕ трактуется как наличие).

Валидация при разборе заголовка (fail-closed, rc=13, до любого запуска):
- malformed-строка заголовка — строка, начинающаяся с keyword+двоеточие
  (`impl:`/`test:`/`docs:`/`edit:`/`accept:`/`reset:`, любой регистр), но не
  проходящая строгую форму этого вида (`accept: x  # комментарий`,
  `Accept: x`, `accept : x`, `reset: maybe`) — ValueError, а НЕ молчаливый
  конец заголовка: потерянная декларация запустила бы машину с неверным
  манифестом (усиление по замечанию внешнего ревьюера, 2026-10-14);
  проза тела, где keyword — не начало строки с двоеточием, по-прежнему
  просто заканчивает заголовок;
- путь проходит те же правила, что и declared-пути (declared_carveout:
  относительный, без `..`, без symlink-компонентов, внутри repo);
- первый компонент — `tests/` (доверенная проверка — тест проекта);
- файл существует ДО запуска (доверие = предсуществование; агент не может
  создать свой собственный оракул);
- путь не объявлен одновременно как impl:/test:/docs:/edit:
  (несовместимые претензии: предсуществующий tests/** файл защищён
  contract lock и CC-206/CC-133 уже запрещают его правку/пересоздание);
- `accept: none` вместе с `accept: <path>` — противоречие (rc=13).

Иммутабельность и происхождение — переиспользование существующей защиты,
без дублирования механизма:
- предсуществующий файл под tests/ ∈ `_protected_files()` → contract lock
  (host-пересчёт против pre-run snapshot) ловит MODIFIED/DELETED ⇒
  CONTRACT-FAIL;
- accept-пути НЕ входят в declared_paths → не карантинятся
  prepare_workspace и не имеют contract-lock-исключения;
- fresh Job (host, без модели) прогоняет полный suite, включая accept-файлы,
  на патченном дереве — независимое исполнение уже существует.

Точка исполнения (единственная новая): `verify_gate` требует, чтобы каждый
accept-путь присутствовал в выводе `run.sh list` (иначе failure
`ACCEPTANCE NOT REGISTERED` — доверенная проверка не будет прогнана никем).
Гейт проверяет РЕГИСТРАЦИЮ (присутствие в `list`), не результат:
зарегистрированный accept-тест, который FAIL, валит вердикт обычной
suite-веткой (`run.sh test --all` rc=1 → failure `(suite)` → DEFECT).
W12 ловит только test-like имена; этот гейт закрывает дыру «доверенный
файл не заявлен ни одной строкой реестра». Именование accept-файлов по
стековому реестру (`tests/**/*_test.py` для py) — обязанность автора
тикета (супервизора); runtime проверяет факт исполнения, а не имя.

Итог: окончательный PASS при `mode=provided` учитывает acceptance-проверки
на трёх эшелонах: неизменность (contract lock), исполнение worker-гейтом
(list + suite), независимое исполнение host fresh Job. При `mode=none|undeclared`
отсутствие независимого свидетельства явно записано в summary.json.

## 3. Рисковая политика (уровень спецификации, не runtime)

- Задачи, меняющие поведение существующего кода: acceptance-сценарии
  (`accept:`) определяются до запуска агента.
- Низкорисковые задачи: допустимы `accept: none` или его отсутствие;
  отсутствие независимых acceptance-тестов должно быть явным
  (`none`/`undeclared` в summary), а не молчаливо принятым за наличие.
- Runtime не классифицирует риск задачи — это суждение автора тикета;
  механизм делает состояние контракта наблюдаемым, не решает политику.

## 4. Non-goals

- Новый верификатор / второй AI-reviewer / обязательный holdout /
  отдельное хранилище тестов — нет.
- Runtime-запрет тикетов без `accept:` — нет (обратная совместимость).
- Runtime-сертификация авторства accept-файла — нет: runtime гарантирует
  предсуществование + неизменность + исполнение; авторство/рецензия —
  решение оператора вне механизма (отмечается в тексте тикета).

## 5. Критерии приёмки и остаточные ограничения

Приято: согласованная схема тикета (grammar + валидация); тесты на
корректный/некорректный контракт; проверки неизменности доверенных тестов
(contract lock, без карантинизации); подтверждение, что PASS учитывает
acceptance-проверки (verify_gate гейт + fresh Job); обратная совместимость
(legacy-тикеты → `undeclared`, поведение не меняется); полный doctor.

Остаточные ограничения (честно):
1. Авторство accept-файла не верифицируется механизмом (только
   предсуществование до запуска и неизменность во время).
2. Рисковая политика — соглашение супервизора; runtime не отказывает
   behavior-change-тикету без `accept:`.
3. `mode=provided` гарантирует, что доверенный файл прогнан и зелёный, но
   не гарантирует содержательную полноту его утверждений (качество теста —
   ответственность автора).
4. Acceptance-гейт в verify_gate — in-Pod; host-эшелон для accept-файлов
   — существующий fresh Job (полный suite), отдельного host-пересчёта
   «accept claimed» нет.
5. Bootstrap-исключение: если `scripts/run.sh` отсутствует (первый тикет
   проекта), entrypoint пишет машина — contract lock её не защищает (он
   защищает только предсуществующие файлы). Корректность bootstrap-
   entrypoint обеспечивается строгим контрактом `test --all` (отказ
   rc=2 валит вердикт; fresh Job прогоняет тот же run.sh), а не lock.
   Accept-контракт в bootstrap-тикете не усиливает это: accept-файл всё
   равно обязан предсуществовать, а исполняется bootstrap-entrypoint'ом.
