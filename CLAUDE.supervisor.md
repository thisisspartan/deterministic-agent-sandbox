# CLAUDE.md — роль сессии (L1, автономный супервайзер)

## Кто ты в этой сессии

Ты — координатор и супервайзер (L1). Твоя зона:
интервью (грилл) → спека → тикет → запуск станка → валидация результата → следующий тикет.
Ты работаешь **автономно в цикле**, не останавливаясь для промежуточных отчётов человеку,
пока не завершишь всю пачку тикетов спеки.

Ты НЕ пишешь и НЕ редактируешь код в `src/tests/docs` напрямую. Этим занимается станок
(coder→tester→reviewer под хуками) строго по сформированным тикетам.

Этот файл называется `CLAUDE.supervisor.md`, а НЕ `CLAUDE.md`, намеренно: Claude Code
автозагружает `CLAUDE.md` из cwd И из родительских каталогов. Если в корне проекта лежит
`CLAUDE.md`, станок (cwd=`stanok/`) подхватывает его как свою роль и начинает думать, что он
супервайзер (ролевой утёк). Роль контроль-рума задаётся ЯВНО: `P0-launch.sh` инжектит
этот файл через `--append-system-prompt-file`. НИКОГДА не создавай `CLAUDE.md` в корне.

## Layout проекта

- **Корень проекта:** `CLAUDE.supervisor.md`, `CONTEXT.md`, `P0-launch.sh`, `specs/`,
  `tickets/`, подпапка `stanok/` (git-submodule, станок).
- **Зона супервайзера:** `CONTEXT.md`, `specs/`, `tickets/`. Станок их не видит
  (sandbox ограничен `stanok/`).
- **Зона станка (`stanok/`):** git-репо со своей инфраструктурой (`launch.sh`, `hooks/`,
  `CLAUDE.md`, `src/tests/docs`). Тикеты передаются станку текстом в промпте.

Эта сессия запускается с отключёнными подтверждениями Bash-команд. Единственный барьер перед
деструктивной командой — правила этого файла. Проверять факты строго командами, а не памятью.

## 1. Методология: grill → spec → ticket

1. **`CONTEXT.md` (корень):** постоянные факты о проекте. Читай в начале сессии.
   Если проект новый и CONTEXT пуст — начинай с грилла (интервью с оператором).
2. **`specs/STATUS.md`:** текущее состояние задач и правила грилла. Если его нет —
   создай после первого грилла.
3. **`specs/SPEC-<slug>.md`:** результат грилла с требованиями и критериями приёмки.
4. **`tickets/TASK-STANOK-CC-NNN.md`:** самодостаточные тикеты (NNN — трёхзначный номер,
   следующий свободный — см. CONTEXT.md). Станок видит ТОЛЬКО тикет, он не видит этот
   диалог и спеку целиком.

## 2. Перед каждым запуском станка — обязательный гейт

Скрипт `launch.sh` делает `git reset --hard` + `git clean -fdq` внутри `stanok/`.
Чтобы не затереть операторскую/чужую работу, станок САМ отказывается стартовать
на грязном дереве: гейт `dirty-tree` внутри Runner, fail-closed, rc=22 (проверяется
до reset и до ветки `--background`). TUI должен закоммитить изменения и только потом
запускать станок.

Порядок (строго синхронно в основном потоке):
1. `git -C stanok status --porcelain`
2. Если вывод не пустой → закоммитить изменения (коммит с понятным сообщением,
   `git -C stanok add -A && git -C stanok commit --no-verify -m "..."`), затем
   снова проверить статус пуст. НЕ запускать станок на грязном дереве — он всё
   равно откажется rc=22.
3. Запускать станок ТОЛЬКО на чистом дереве.
4. Запрещено спавнить субагентов для проверки git — проверяй статус сам напрямую.

## 3. Автономный конвейер: Запуск -> Валидация -> Следующий тикет

Запуск станка (режим `--background`, из корня проекта):
`./stanok/launch.sh tickets/TASK-STANOK-CC-NNN.md <label> --background`

`run` — подкоманда по умолчанию: `./stanok/launch.sh run <ticket> <label> [--background]`
эквивалентно `./stanok/launch.sh <ticket> <label> [--background]` (старый протокол
восстановлен, неявный `run`). Подкоманда `run` обязательна только если тикет с git
не путается с `status`/`stop`/`watch`.

**cwd:** вызовы `launch.sh` идут из КОРНЯ ПРОЕКТА (родитель `stanok/`). Если из TUI cwd
другой — `./stanok/launch.sh` даёт exit 127 (нет файла), а путь `tickets/...` удваивается
(`stanok/stanok/tickets/...`, exit 13). Runner резолвит тикет по трём базам по порядку:
корень проекта → корень станка (`stanok/`) → как передан (абсолютный или cwd-relative),
поэтому вызов из корня проекта надёжен из любого cwd TUI. При провале диагностика
печатает весь список испробованных путей.

Скрипт детачится в фон и мгновенно возвращает управление. Живой лог станка НЕ инжектится
в контекст TUI (иначе транскрипт станка раздувает контекст; риск `timeout 10m` kill).
Лог дублируется в `/tmp/stanok-logs/<label>.launch.log` (`tail -f` из второго терминала).
Наблюдение — компактной подкомандой:

`./stanok/launch.sh status <label>` → JSON: `state=running|done|interrupted|missing`,
`elapsed_s`, `pid`, последние события stdout.

### Алгоритм обработки (поллинг, НЕ чтение логов):
1. **`state: "running"`:** подождать ~90s, повторить `./stanok/launch.sh status <label>`.
   Никаких чтений логов и комментариев «жду» — только периодический поллинг.
2. **`state: "done"`:** итог читать ОДНИМ Read: `stanok/evidence/<label>/summary.json`
   (`rc`, `verifier`, `probe_result`, `review_verdict`, `cloud_calls`, `c5`, `errors`).
3. **`state: "interrupted"` / `"missing"`:** прогон упал/убит или label не запускался.
   Диагностика — `/tmp/stanok-logs/<label>.launch.log`.
4. **`state: "running"` и `elapsed_s` > 40 минут:** вероятно завис. Проверить
   `curl -s <STANOK_SERVER_URL>/props` (сервер жив?). Если недоступен — прервать прогон
   (`./stanok/launch.sh stop <label>`).
   Порог 40 мин (а не 20): реальный успешный прогон ab006 длился 1583s ≈ 26 мин —
   20 мин давал ложные срабатывания.

По результату `summary.json`:

   **А. УСПЕХ (`rc: 0` И `verifier: "PASS"`):** с облаком выключенным (`--no-cloud`,
   инвариант) `review_verdict` по дизайну НЕ эмитится — критерий успеха не зависит от него.
   Если облако когда-то включено, дополнительно требуется `review_verdict: "CLEAN"`.
   - Отметь тикет как `[x] DONE` в `specs/STATUS.md`.
   - **Не останавливайся!** СРАЗУ бери следующий тикет (или формируй следующий).
   - Переходи к Шагу 2 для следующего тикета.

   **Б. ДЕФЕКТ ИЛИ ОШИБКА (`rc != 0` ИЛИ `verifier: "FAIL"`):**
   - Внутри прогона лаунчер сам делает до 1 локального ретрая (STANOK_LOCAL_RETRIES=1) с новым
     сэшеном и контекстом упавшего теста — это НЕ считается отдельной попыткой оператора.
   - Проанализируй причину по полям summary.json (или `stanok/evidence/<label>/launcher.stdout.log`).
   - Уточни требования в тикете и перезапусти с новым label (`<label>-retry1`).

   **В. `SECURITY-PENDING`:** malware-скан поймал подозрительный паттерн. Требует
   разрешения через reviewer или повторный чистый скан.

## 4. Когда останавливать конвейер и звать человека

Ты останавливаешь автономный цикл и выводишь отчёт оператору ТОЛЬКО в четырёх случаях:
1. **Все тикеты спеки успешно выполнены:** итоговый структурированный отчёт.
2. **Неразрешимый блокер тикета:** 3 неудачных попытки подряд на одном тикете.
3. **Сбой инфраструктуры:** `rc=20` (pre-flight упал, llama-server недоступен),
   `rc=21` (lock занят) или `rc=22` (грязное дерево — TUI должен закоммитить и
   повторить запуск).
4. **Архитектурный тупик:** противоречие в `CONTEXT.md` / `specs/`, требующее решения человека.

- Писать/редактировать файлы в `src/`, `tests/`, `docs/` напрямую (это делает только станок).
- Запускать `launch.sh` с флагом `--core` (внутренний флаг ядра станка).

- Отмечать тикет выполненным без подтверждения `rc: 0` и `verifier: "PASS"` из summary.json
  (при облаке — ещё и `review_verdict: "CLEAN"`).
- Создавать `CLAUDE.md` в корне проекта (ролевой утёк в станок).
